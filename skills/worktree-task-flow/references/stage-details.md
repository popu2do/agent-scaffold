# Stage Details

按需读取这个文件，不要默认整份加载。

## 何时读取

- 用户追问“为什么回到上一阶段”
- 用户要求一版更完整的阶段汇报
- 你发现 `base_branch / integration_target / remote_scope` 存在歧义

## 前置处理细则

- `base_branch` 是 worktree 的起点，不等于最终合入目标。
- `integration_target` 是最终要落点复核的分支。
- `remote_scope` 默认按最保守处理；如果用户没明确授权，不默认碰 `origin/*`。
- `worktree_root` 由前置参数统一确定，后续阶段保持一致。
- 如果改动误落到主工作区，先纠正隔离，再继续任务。

## 需求分析细则

- 文档驱动仓库先读 spec，再动代码。
- bug 排查优先复现、对日志、看样例数据，不要因为“猜得像”就跳实现。
- 一旦发现之前理解错了，应回到本阶段修正结论。

## 方案设计细则

- 优先根因修复。
- 除非有明确硬需求，否则不要引入兼容、回退、防呆、双轨逻辑。
- 如果要改动多层或多模块，先说明影响面和验证策略。

## 目标对齐细则

- 对齐内容尽量短，聚焦：目标、结果、业务影响、已完成、待完成、风险。
- 如果用户要求每阶段确认，在这里停下。
- 如果实现中需求新增、缩减或偏移，回到分析或设计阶段，不临时打补丁。

## 实现与验证细则

- 先最小实现，再补测试与文档。
- 先跑最窄相关测试，再按风险扩大。
- 汇报时分开写：通过、失败、未跑、残留风险。
- 如果测试结论推翻方案，不要硬推，回到前一阶段。

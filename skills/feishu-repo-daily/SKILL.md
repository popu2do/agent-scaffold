# Feishu Daily Report

## 目标

生成可直接发送的飞书日报。

核心原则：**日报项目来自已登记仓库清单，git commit 是唯一事实来源。**

日报只写已经发生且可追溯的结果，不写聊天过程、命令过程、排障流水账、环境问题。

推送使用 `scripts/push_feishu_daily.py`。

## 强约束

以下规则是 **硬性 contract**，不是参考示例：

1. 产出日报草稿时，必须严格使用本技能定义的固定模板。
2. 用户纠正后，默认只允许修改事实、措辞、项目归类和条目内容，**不得擅自修改模板骨架**。
3. 每次纠正后，必须重新输出一份 **完整草稿**，不能只回局部修改片段。
4. 如果用户没有明确要求改模板本身，就必须保持标题、顺序、段落结构、分隔线和结尾提问一致。
5. 任何自检项未通过时，禁止推送；必须先重写草稿，再重新征求确认。
6. 未展示本轮完整草稿前，禁止推送。
7. 只有在展示完本轮完整草稿后，收到用户对当前 `是否推送到飞书？(y/n)` 的直接确认，才允许推送。

## 流程

1. 读取当前技能目录下的 `projects.json`。
2. 按清单中的项目名和仓库路径逐个确认 git 根目录。
3. 读取这些仓库在日报时间窗口内的 commit、变更文件和必要 diff。
4. 按登记的项目名生成业务可读日报草稿。
5. 展示完整草稿并询问是否推送。
6. 只有在用户明确确认后，才调用飞书推送脚本。

## 取证

### 1. 读取项目清单

必须读取：

```text
<skill-dir>/projects.json
```

清单规则：

- `report_name`：日报里使用的项目名。
- `repo_path`：本地仓库路径。
- 项目名以清单记录为准，不要使用文件夹名代替。
- 如果用户提醒项目名不对，应更新清单，不要临时硬编码在日报逻辑里。
- 多项目输出顺序默认与 `projects.json` 顺序一致，不要每次自由重排。

### 2. 确认仓库

```powershell
git -C "<repo_path>" rev-parse --show-toplevel
```

只保留有效 git 仓库根目录。

### 3. 读取 commit

默认按 `昨天 18:00:00` 到 `今天 18:00:00` 的日报窗口查询 commit。

```powershell
git -C "<项目根目录>" log --since "yesterday 18:00:00" --until "today 18:00:00" --date=iso --no-merges --pretty=format:"%H%x09%an%x09%ae%x09%ad%x09%s"
```

对命中的 commit 读取统计和文件清单：

```powershell
git -C "<项目根目录>" show --stat --name-status --format=fuller "<commit_sha>"
```

只有标题和文件清单无法判断业务含义时，才读取相关文件 diff：

```powershell
git -C "<项目根目录>" show --format=medium --unified=80 "<commit_sha>" -- "<相关文件>"
```

如果项目已登记，但当前日报时间窗口内没有 commit，不要编造成果。

## 总结规则

每条日报必须能回到当前日报时间窗口内的 commit，写清楚实际发生的业务改动，不写操作过程。

日报按读者能理解的语言说明已完成的事及其直接影响；仅在有助于理解结果时保留技术细节，且不得超出已核实事实。

优先写：

- 功能、脚本、skill、文档、配置或流程的明确更新。
- 已修复的问题。
- 已完成的验证、发布、同步或可复用产出。
- 评审结论、方案收敛、风险收敛。

不要写：

- “优化代码结构”“提升稳定性”“完善能力”等空话，除非说清具体对象和结果。
- “完成相关开发”“处理若干问题”“推进项目工作”等看不出更新内容的话。
- 命令失败、依赖下载、鉴权、网络、环境清理等过程问题。
- git 推送、远端配置、分支处理、临时目录清理等仓库操作。
- 文件名、函数名、类名堆砌，除非日报对象本身就是脚本、文档或专项工具。
- 未经证实的泛化表述，例如“提升体验”“增强稳定性”。

多项目按项目分组。项目很多时，每个项目只保留最重要的 1-2 条。

## 固定模板

### 有 commit 证据

输出时必须严格使用下面这份模板，标题、顺序、空行、分隔线和结尾提问都不能改：

```text
今日日报内容：

【今日总结】
【项目或专项名称】
1. [做成了什么 / 修复了什么 / 形成了什么可复用产出]
2. [做成了什么 / 修复了什么 / 形成了什么可复用产出]

【明日计划】
无

【需要协调与帮助】
无

---
是否推送到飞书？(y/n)
```

换行要求：

- `【今日总结】` 后必须换行，再输出每个项目标题。
- 每个项目标题必须独占一行；项目标题与第一条编号之间保留一个换行。
- 每条编号必须独占一行；同一项目的多条编号不得拼接在同一行。
- 不同项目之间保留一个空行。
- `【明日计划】`、`【需要协调与帮助】`、分隔线和推送确认语必须分别独占一行，并保持模板中的空行结构。
- 调用推送脚本时，`--today`、`--tomorrow` 和 `--help-needed` 参数必须传入与已展示草稿一致的多行文本，不得将项目或条目压成单行。

约束：

- `【今日总结】` 必须放在最前。
- 每个项目都必须使用单独的 `【项目或专项名称】` 标题块，不能和别的项目混写。
- 总条数默认 3-5 条。
- `明日计划` 默认写 `无`；只有 commit、当前线程或用户明确留下待办时才写。
- `需要协调与帮助` 默认写 `无`；只有明确需要他人、跨团队或业务决策介入时才写。
- 如果用户纠正了内容，必须基于同一模板重新输出完整草稿。
- 不允许把 `是否推送到飞书？(y/n)` 改成模糊说法，例如“要不要发”“是否提交”“要不要同步”。

### 无可用 commit

```text
今日日报内容：

今天已检查已登记仓库，但未找到可用于日报的当天 git commit 记录。为避免编造成果，本次不生成日报草稿，也不推送飞书。
```

### 无有效仓库

```text
今日日报内容：

当前项目清单中没有可用仓库，本次不生成日报草稿，也不推送飞书。
```

## 用户纠正处理

当用户对草稿提出纠正时，按下面规则处理：

1. 纠正事实：替换对应条目内容，然后按固定模板重新输出完整草稿。
2. 纠正措辞：替换对应条目内容，然后按固定模板重新输出完整草稿。
3. 纠正项目归类：调整项目块归属，然后按固定模板重新输出完整草稿。
4. 纠正条目数量：增减条目后，仍然按固定模板重新输出完整草稿。
5. 只有当用户明确说“改模板”“换格式”“以后按这个新结构写”时，才允许修改模板本身。

如果用户只是说“这条别这么写”“这句改一下”“进行中不要写成已完成”，这属于 **内容纠正**，不是模板变更。

## 推送

推送脚本：

```text
<skill-dir>/scripts/push_feishu_daily.py
```

明确确认仅包括：

- `y`
- `yes`
- `确认`
- `继续`
- `推送`

但这些词只有在 **本轮完整草稿刚展示完之后**，且明显是在回答 `是否推送到飞书？(y/n)` 时才算有效确认。历史消息、别的上下文里的“确认”“继续”都不能拿来当推送许可。

没有“需要协调与帮助”时：

```powershell
"<python-executable>" "<skill-dir>/scripts/push_feishu_daily.py" --today "[今日总结]" --tomorrow "[明日计划]"
```

有“需要协调与帮助”时：

```powershell
"<python-executable>" "<skill-dir>/scripts/push_feishu_daily.py" --today "[今日总结]" --tomorrow "[明日计划]" --help-needed "[需要协调内容]"
```

如果脚本提示未登录或登录失效，先询问用户是否进入登录流程；确认后执行：

```powershell
"<python-executable>" "<skill-dir>/scripts/push_feishu_daily.py" --login
```

## 推送前阻断自检

推送前必须逐项自检。任一项不满足，禁止推送，并重新输出修正后的完整草稿：

- 项目来源仅为 `projects.json`，没有再依赖会话记录。
- 每个项目都已确认 git 根目录。
- 日报项目名来自清单记录，而不是文件夹名。
- 每条日报都有当前日报时间窗口内的 commit 证据。
- 语言风格已转换为通俗业务语言（说人话），严禁堆砌文件名、类名、函数名、内部服务标识或架构术语。
- 已去掉过程噪音、空话和无法证明的成果。
- 已按固定模板输出，没有改标题、顺序、空行、分隔线和结尾提问。
- 如果用户做过纠正，当前展示的是纠正后的 **完整草稿**，不是局部片段。
- 已在本轮草稿后明确询问 `是否推送到飞书？(y/n)`。
- 已收到针对本轮草稿的直接确认。

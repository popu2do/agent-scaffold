# Release Notes Push

## 目标

把代码变更整理成用户可以直接阅读和发布的更新说明。正文以实际可感知的变化为中心，保留必要事实，省略实现过程和内部治理信息。

## Quick Start

1. 确认输入：可执行的 `git range`、起止版本或提交标识、目标平台和页面信息。
2. 运行 skill 目录下的 `scripts/collect_git_range.ps1`，收集提交、文件和统计上下文。
3. 按 [FILTER_RULES.md](FILTER_RULES.md) 筛选用户可感知的变化。
4. 按 [TEMPLATE.md](TEMPLATE.md) 组织成稿。
5. 按 [TARGETS.md](TARGETS.md) 渲染到目标平台；远端写入前完成发布确认。

## 工作流程

### 1. 收集事实

- 优先依据真实 Git 记录，不直接翻译 commit message。
- 至少收集提交列表、`diff --stat`，以及关键提交的变更文件和统计信息。
- 用户提供版本标识时，在目标提交的历史链上解析最近的版本边界。

### 2. 筛选变化

保留以下内容：

- 用户可以看到的新入口、新动作或新结果。
- 用户实际会遇到的问题修复。
- 兼容范围、支持对象或执行结果的变化。

过滤以下内容：

- 测试、覆盖率、CI、发布脚本和权限治理等内部工程变更。
- 只改变代码组织方式、模块边界或命名方式的重构。
- 无法独立表达用户结果的中间修补提交。

### 3. 组织正文

正文按照以下顺序组织：

1. 标题、更新时间和版本范围。
2. `更新内容`：按用户可感知程度排序，写 1-4 条核心变化。
3. `升级提示`：仅在存在迁移、兼容条件、额外操作或已知限制时追加。

写作规则：

- 以版本范围的起点作为主要参照，优先描述相对于基线发生的变化。
- 版本中没有变化的既有能力通常不单独列为更新点；如果有助于说明兼容边界，可以作为简短背景保留。
- 每条只表达一个变化，优先使用“变化标题：具体结果”的句式。
- 新功能说明用户现在可以做什么。
- 修复说明原来的异常和现在的结果。
- 兼容范围扩大时说明新增支持对象；兼容范围收窄时突出被移除的能力，并视需要补充受影响对象和用户操作。
- 只有一个核心变化时只写一条；内容少不补写无关事项。
- 先写结果，再补必要背景；不把实现过程写成用户收益。
- 使用冷静、事实性的中文，不写感受、推测或未经验证的收益判断。
- 默认不写文件路径、模块名、脚本名、命令名、参数名、类名和 tag；用户明确要求技术版时再展开。

成稿检查：

- 读者能看出改了什么。
- 读者能看出会在哪个使用场景遇到变化。
- 每条内容都能由 Git 事实或已验证结果支撑。
- 每条主要变化都能回答“相对于起始版本，什么发生了改变”。
- 删除任何一条后，剩余内容仍保持清晰，不需要重复解释上下文。

### 4. 输出到目标平台

- GitLab Wiki 和 Confluence 使用同一份通用正文，只做格式转换。
- 页面默认使用独立的版本页面，标题包含版本标识。
- 首页只维护版本页面入口，不复制完整正文。
- 具体平台规则见 [TARGETS.md](TARGETS.md)。

### 5. 发布安全

- 任何远端写入前都必须获得用户明确确认。
- 发布前确认目标平台、页面标识、首页入口策略和覆盖策略。
- GitLab Wiki 使用 skill 目录下的 `scripts/publish_gitlab_wiki.py`。
- Confluence 使用 skill 目录下的 `scripts/markdown_to_storage.py` 和 `scripts/publish_confluence.py`。
- 未完成发布确认时，只生成本地成稿，不执行远端写入。

# 过滤规则

## 默认过滤

以下变更通常不进入更新说明正文，除非用户明确要求保留：

- 只影响内部研发流程，不改变使用者看到的入口、步骤、结果或提示
- 只影响代码组织方式，不改变实际使用行为
- 同一问题的连续修补里，不能单独形成最终结果的零碎变更
- 只补充内部文档、规则、门禁、测试覆盖，而没有带出使用侧变化

## 默认保留

以下变更通常应进入更新说明正文：

- 使用者会直接看到的新入口、新动作、新结果
- 使用过程中会直接遇到的问题修复
- 兼容范围、支持对象或执行结果发生变化的调整
- 数据输入、结果输出、提示反馈这类使用链路上的明显变化

## 归并规则

- 多个 commit 修同一类问题时，归并为 1 条结果描述。
- “重构 + 修复”同时出现时，优先保留“修复了什么问题”。
- 多个适配或兼容调整如果落到同一使用结果，可归并为 1 条“支持范围变化”。

## 变化判定

- 以版本范围起点的用户能力和兼容范围作为主要参照，更新说明优先写相对基线发生的变化。
- 版本中保持不变的能力通常不单独构成更新点；如果能帮助读者理解边界，可以作为简短背景保留。
- 兼容范围收窄时，应突出被移除或不再支持的能力；保留的兼容路径可按需要作为补充说明。
- 兼容范围扩大时，标题和首句应直接写明新增支持的对象或格式。

## 禁止事项

- 不直接复制 commit message 给终端用户。
- 不把纯工程噪音包装成使用价值说明。
- 不在未验证时声称“性能提升 x%”这类定量结果。
- 不把“分析过程”当成最终汇报正文，例如提交范围、提交数量、过滤过程、版本拆解说明。
- 不把开发实现名词直接端给普通读者，例如脚本名、模块路径、命令名、tag、编码格式、参数名。
- 不使用抽象评价替代事实；凡是不能回答“改了什么”的句子，都不能直接入稿。

## 快速判断

- 能进入最终正文的内容，必须至少满足下面之一：
  - 使用者会多一个动作可以做
  - 使用者少一个错误会遇到
  - 使用者面对同一步骤时，看到的结果发生了变化
- 如果一条内容只有“内部更整齐、更统一、更规范”，默认过滤。
